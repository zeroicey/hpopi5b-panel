# 新闻幕：数据源 = 头条热榜（退化百度）+ 三路科技 RSS，两列各一源

**Status:** ✅ ACCEPTED · **Date:** 2026-11-08 · **Deciders:** owner（三问三答）+ AI 实测选源 · **Supersedes:** none

## Context

用户要「加一幕新闻」，先问「数据源选哪里？要哪种新闻？」。既有约束：渲染路径**永不联网**
（`trending` 已经是「timer 抓 → 缓存 TSV → 幕只读」），CPU 与内存预算不能为这一幕破坏；
kiosk 无键鼠，30s 一轮换。选源必须在 **hpopi5b 上实测**，不能按文档假设（2026-11-08）。

用户答复：上屏形态**两列**、抓取频率 **30 分钟**、两列分法**左「国内热点」/ 右「科技」**。

## Options

| Option | Upside | Downside | Reversibility |
| --- | --- | --- | --- |
| A 头条热榜 + 百度热搜（退化） | 200、50 条、带热度值、无需 key | **无分类字段** ⇒ 掺体育/娱乐；热榜口径随平台变 | easy（换 `--hot` 源即换） |
| B 微博热搜 / 知乎热榜 | 更「新闻」 | 403 / 401；`m.weibo.cn` 直接回「Sina Visitor System」登录墙 | — 不可用 |
| C 正规媒体 RSS（人民网/新浪/新华社/中新网/界面） | 有分类、可挑时事 | 人民网 pubDate 停在 2025、新华社只剩 1 条、新浪 1 条；只有中新网/界面新鲜（30 条） | easy |
| D Google News / RSSHub / HN 官方 RSS | 聚合 | 000（TLS / 注册墙 / 超时） | — 不可用 |
| E 科技：Solidot + 少数派 + 36氪 | 已可用、内容质量高 | 36氪 feed 解析 0 条 | easy（加一路只改脚本） |

## Decision

1. **左列 = 头条热榜**（`hot-event/hot-board`，失败退化百度热搜），列「标题 + 热度（万）」。
   接受「会掺体育/娱乐」——那是热榜形状，不是排版问题；**不在热搜上做关键词过滤**（假分类）。
2. **右列 = 科技**：Solidot + 少数派 + 36氪 合并、去重、按 pubDate 倒序，列「标题 + 来源 · 相对时间」。
3. **架构照 `trending`**：`tools/fetch-news.py` 由 `hpopi5b-news.timer`（30 分钟）跑，原子写
   `/var/cache/hpopi5b-panel/news.tsv`；`src/scene_news.c` 只 `stat()` + 读文件，
   缓存没变就一分钟才重画一次。抓不到保上一份，**永不灌假数据**。
4. 顶栏诚实报「N 分钟前同步 · 热点 N · 科技 M」；>90 分钟转 `C_YELLOW`（3 个抓取周期 ⇒ 该看日志了）。
5. 「右对齐的量化值」在榜单幕统一 `C_YELLOW`（trending 的「+X★」、news 的「1337万」），
   **不借 `C_PEACH`**（那是网络上行）。

## Consequences

- 想看「纯时事」⇒ 换 `--hot` 的源（已实测 `chinanews` / 界面 RSS 新鲜），不用改 C 代码。
- 热度列只有热榜能给；换 RSS 源后左列右值要变成「时间」，`scene_news.c` 的右值列宽（`L_NW_RIGHT_W 132`）够用。
- 多了一个 python 脚本要与二进制**分开**部署（`docs/deploy.md` ③b），漏装只会让幕停在旧缓存。
- 轮换周期变 3 幕 × 30s = 90s，仍低于 `scenes.c` 注释里 2 分钟的红线。

## Revisit when

- 头条热榜接口失效（连续 ≥3 个周期 `hot=0`）⇒ 换百度或直接改走 C 方案。
- 用户抱怨「体育/娱乐太多」⇒ 那不是调参能解决的，是**换源**，回到本文件的 Options 重新裁。
- 想在左列加分类（财经/国际/体育分区）⇒ 需要能带分类的源（中新网/界面 RSS 各自成列），等于重排版式。

## 修订 2026-11-09：版式两列 → 三列 + 首条放大（✅ ACCEPTED）

用户口径（原话）：「感觉看起来的效果一般般很单调 空间利用率不够 国内热点和科技这一行标题可以删掉了」。
给了三个方案让用户选：A 三列 + 首条放大、B 两列压紧 + 纹理（条/徽标）、C 四列高密度；**用户选 A**。

| 决策 | 为什么 |
| --- | --- |
| 热点 1 列（34%）+ 科技 2 列，删掉列标题行 | 两列各 15 条时行距空荡、整屏只装 29 条；三列装 41 条，分组靠列宽 + 竖细线，不用小标题占一条 26px |
| 两行式 44px（标题 + 刻度杆 / 来源） | 40px 装不下「13pt 行高实测 24 + 9pt 16.6」，会压字（本轮踩过）；杆给了「非数值可比的量」一个位置 |
| 首条 92px + 17pt 两行 wrap + 210px 杆 | 需要「一眼能读」的锚点，否则满屏同权重的条目 |
| 杆**左端钉死**在标题起始 x、长度封顶 150（首条 210） | 共用基线才可比；右对齐到数字会让杆从标题中段长出来；铺满整列就成了「高亮下划线地毯」 |
| 行间细线只画在科技列 | 热点列第二行就是杆，再叠一条是双线噪声 |
| 顶栏报「上屏条数」而非缓存池大小 | 抓 20 条只展示 13 条时写 20 是误导（诚实原则的延伸） |
| `scene_t.live = 0`（news/trending） | 采样快照无条件进全局签名会让这两幕每秒整屏重绘：实测 2.94% → 2.01%（见 `docs/pitfalls.md` 24） |

**代价**：`fit()` 二分截断 + 首条 wrap 让单帧绘制从 6ms 涨到 ~20ms —— 但只在「分钟翻转 / 缓存改写」时发生，
实测总 CPU 反而降了（见上）。若要再压，优先减少 `v_text` 调用次数（合并科技列的「来源 + 时间」为一条字符串）。
